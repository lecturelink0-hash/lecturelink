# 0-f 이미지 캡션 경로 결정 (RAG 실행계획 v1.1 · PR F)

2026-10-02 · 전재현 · 도구: `scripts/rag-eval/caption-eval.ts` · 적용: `lib/extract/caption-image.ts`, `lib/rag/caption.ts`

## 결론

- **캡션은 크롭당 Vision 1콜(후보 C)로 만듦.** 크롭 OCR 콜에 캡션 필드를 덧붙이는 안(후보 A)은 추가 콜이 없어 원가가 더 낮지만, OCR 글자와 글자 박스가 크게 망가져 사전 기준 6개 중 4개에 미달함. 박스는 정답 단서 라벨을 지우는 마스킹 좌표라 OCR 콜은 건드리지 않음.
- **원가는 크롭당 약 $0.0001임**(gemini-2.5-flash-lite). 10문항 이미지형 업로드(문항 이미지 후보 10장 안팎)라면 업로드당 약 $0.001, 문항당 약 $0.0001로 기준선 $0.0241의 0.4% 수준임.
- **지연은 늘지 않음.** 캡션 콜 중앙값은 1.3초로 OCR(2.2초)보다 짧고, OCR과 같은 시점에 따로 돌아 OCR 대기 안에 끝남.
- **품질.** 캡션 생성률 100%(70/70)임. 캡션으로 같은 자료의 본문 청크를 찾으면 크롭 페이지(±1)가 3위 안에 드는 비율이 0.77로, OCR 글자(0.64)보다 높음. 글자가 거의 없는 그림(OCR 20자 미만)에서는 0.78 대 0.36으로 차이가 큼.
- **운영 DB에서 확인함.** 이 브랜치로 IM1을 shadow로 돌려 캡션 청크 저장, 임베딩, `modality` 필터 검색까지 확인했고, 업로드 원가·처리 시간·형식 위반율은 off 실행 간 차이 안에 있었음(4장).
- **이미지형 요청 + `PRIVATE_RAG_MODE` shadow·on에서만 동작함.** `off`의 동작·원가는 바뀌지 않음. 계획서 9장은 F가 `off`에도 영향을 준다고 봤지만(Vision 출력 스키마 변경), OCR 콜을 건드리지 않게 되어 그 영향이 없어짐.

## 1. 후보와 비교 방법

계획서 0-f는 "기존 콜 확장 vs 후보 이미지당 1콜 추가" 중 원가가 낮은 쪽을 고르라고 함. 코드를 다시 보니 기존 콜 중 확장할 가치가 있는 것은 크롭 OCR 콜이었음.

| 기존 콜 | 덮는 크롭 | 판단 |
|---|---|---|
| 의료 이미지 검출(`detectMedicalRegions`) | 페이지 렌더 경로만 | 임베드 경로(운영 PDF 대부분)를 못 덮음. 제외 |
| 이미지 선별(`selectExamImages`) | 임베드 경로만, 320px 썸네일 | 계획서대로 캡션 품질 부족. 제외 |
| **크롭 OCR(`runOcr`, 좌표 모드)** | **두 경로의 모든 크롭, 원본 해상도** | 후보 A로 비교 |

- **후보 A:** OCR 프롬프트 끝에 `"image":{image_type, caption, findings}` 키를 덧붙임(부록에 문구 그대로 둠).
- **후보 C:** 기존 콜은 그대로 두고 크롭마다 캡션 전용 1콜을 추가함(`captionPrompt`).
- **측정:** 골든셋 5건(SL1·SL4·NT1·SC2·IM1), 크롭 50개. 운영과 같은 추출 경로(`extractFromBuffer`, 이미지형)로 크롭을 만들고 크롭마다 OCR 기준 2회(B1·B2), A, C를 부름. B1과 B2의 차이를 잡음 바닥으로 씀.
- **판정 기준은 실행 전에 적어 둠.** A가 6개를 모두 충족하면 A, 하나라도 어기면 C를 쓰기로 함.

## 2. A vs C 결과 (크롭 50개)

| 항목 | 잡음(B1↔B2) | A | 기준 | 판정 |
|---|---|---|---|---|
| OCR 글자 유사도 평균 | 1.000 | 0.774 | ≥ 0.980 | 미달 |
| 글자 박스 면적 재현율 평균 | 1.000 | 0.758 | ≥ 0.980 | 미달 |
| 재현율 0.9 미만 크롭 | 0% | 59.5% | ≤ 5% | 미달 |
| 텍스트 캡처 판정 일치 | 1.000 | 0.898 | ≥ 0.970 | 미달 |
| JSON 형식 실패 | 2% | 2% | ≤ 4% | 충족 |
| 캡션 생성률 | — | 44% (C 100%) | ≥ 90% | 미달 |
| 캡션-페이지 정합 top-3 | — | 0.818 (n=22) vs C 0.840 | A ≥ C − 0.05 | 충족 |

- **원가.** 크롭당 A의 증분은 $0.000048(OCR $0.000316 → $0.000364), C는 $0.000101임. A가 반값이지만 차이는 업로드당 $0.0005 수준임.
- **B1과 B2가 완전히 같음**(temperature 0). 그래서 A의 차이는 전부 프롬프트 때문임.
- **A가 망가뜨린 것.** 9/50 크롭에서 OCR 어절의 20% 넘게가 빠짐. 예를 들어 식도 내압 그래프에서는 'Pharynx', 'Upper esophageal sphincter' 같은 축 라벨이 빠졌음. 빠진 라벨은 박스도 없어 마스킹되지 않으므로, 학생 화면에 정답 단서가 남을 수 있음.
- **캡션도 절반 넘게 빠짐.** 모델이 OCR 형식에 맞추느라 `image` 키를 자주 생략했음(자료별 3/10~6/10).

## 3. C 확대 측정 (골든셋 5건 + 추가 2건, 크롭 70개)

추가 2건은 심낭질환(N2)과 인터벤션·혈관영상(N3) 강의록임. 골든셋 원본과 같은 폴더에 있는 파일임.

| 항목 | 값 |
|---|---|
| 원가 | 크롭당 $0.000099 (입력 601 · 출력 96 토큰) |
| 지연 중앙값 | 캡션 1.33초 / OCR 2.16초 |
| 캡션 생성률 | 100% (70/70), 오류 0 |
| 캡션 청크 길이 중앙값 | 117자 |

**페이지 정합.** 캡션(또는 OCR 글자)을 질의로 같은 자료의 본문 청크를 voyage-4로 찾았을 때, 크롭이 나온 페이지(±1)의 청크가 1위·3위 안에 드는 비율임.

| 그림 | OCR 글자 top-1 / top-3 | 캡션 top-1 / top-3 |
|---|---|---|
| 전체 | 0.48 / 0.64 (n=58) | 0.53 / 0.77 (n=70) |
| 글자 20자 미만 | 0.18 / 0.36 (n=11) | 0.52 / 0.78 (n=23) |
| 글자 20자 이상 | 0.55 / 0.70 (n=47) | 0.53 / 0.77 (n=47) |

- OCR이 글자를 하나도 못 읽은 크롭 12개는 OCR로는 찾을 방법이 없음. n이 다른 이유가 이것임.
- 조직 사진, 내시경 사진, 영상처럼 글자가 없는 그림일수록 캡션이 필요함. 이미지 문항이 주로 쓰는 그림도 이쪽임.

## 4. 운영 경로 확인 (IM1, 운영 DB)

골든셋 하네스(`golden-run.ts`)로 이 브랜치 코드를 운영 DB에 붙여 IM1(이미지형 포함 10문항)을 돌림. shadow 2회, off 1회를 돌리고 G0 off 3회와 비교함. 테스트 업로드는 확인 후 지움.

| 실행 | 문항 | 업로드 원가 | 처리 시간 | 캡션 콜·비용 | 캡션 청크 | 형식 위반율 |
|---|---|---|---|---|---|---|
| G0 off (3회) | 10·10·10 | $0.442·0.387·0.394 | 146·146·131초 | — | — | 20·20·10% |
| 이 브랜치 off (1회) | 10 | $0.395 | 129초 | 0 | 0 | 20% |
| 이 브랜치 shadow (2회) | 10·10 | $0.318·0.404 | 147·154초* | 10콜 · $0.0010 | 10·10 | 10·30% |

\* 2회차는 생성 모델 503(수요 과다)으로 선발 배치 1개를 재시도함.

- **캡션 원가.** 업로드 원가의 0.3%임. 같은 실행의 청크 임베딩(126청크, $0.00096)과 비슷한 크기임.
- **처리 시간.** 추출 완료 시점(18.3·23.3초 vs off 17.6~19.6초)과 처리 시간 모두 off 실행 간 차이 안에 있음.
- **off는 바뀌지 않음.** 캡션 콜 0, 청크 종류는 본문·OCR만으로 종전과 같음.
- **형식 위반율.** 계획서 9장의 F 회귀 지표로, 회차당 10문항이라 한 문항이 10%p임. shadow 평균 20%는 G0 off 범위(10~20%) 안팎임. 캡션은 생성 입력에 들어가지 않으므로 형식 위반율이 달라질 경로도 없음.
- **DB 확인(shadow 1회차).**
  - 캡션 청크 10개가 116~125번(본문 109 → OCR 7 → 캡션 10)으로 저장됨. `kind = modality = image_caption`이고 `image_id` 10개가 모두 서로 다름. 본문·OCR 행에는 `image_id`가 없음.
  - 10개 모두 voyage-4로 임베딩됨(`embedding_sha = content_sha`).
  - `match_material_chunks(p_modality => ['image_caption'])`가 캡션 청크만 돌려주고, 1위가 질의한 그 청크임.

## 5. 구현

- **언제 만드나.** `wantsImages && ragIndexingEnabled(RAG_MODE)`일 때만 만듦. 대상은 `captionEligible` 크롭(페이지 전체 OCR 폴백, 텍스트 캡처 분류 제외)임.
- **언제 부르나.** 크롭 OCR이 출발하는 시점에 같이 출발함. 동시성은 OCR과 따로 6이고, OCR 대기에서 함께 기다림(상한 60초).
- **어떤 그림을 넣나.** 표시용 원본 색상 크롭을 넣음. OCR 전처리본은 심전도·X-ray를 흑백으로 바꿔 색 정보가 사라짐.
- **청크로 남기는 범위.** 문항 이미지 후보(featured) 중 캡션을 받은 그림만 청크가 됨. 후보 밖 크롭은 문항에 쓸 수 없어 검색에 걸려도 소용이 없음. 그래서 featured 확정을 청크 저장 앞으로 옮김. 크롭·OCR 결과만으로 정해지는 계산이라 결과는 같음.
- **청크 형식.**
  - `kind = modality = image_caption`이고, 본문 → OCR → 캡션 순서로 맨 뒤에 붙음. 캡션을 빼도 앞 청크의 번호·id는 그대로임.
  - 본문은 `[이미지: 그림 종류] 캡션` 뒤에 `소견: …`이 붙음.
  - `image_id`는 (업로드, 크롭 PNG 지문)의 UUID v5임. 그림만 따로 저장하는 표가 없어서 외래키 대신 계산값으로 둠.
- **00045 컬럼.** shadow·on에서는 `modality`·`image_id`를 매번 씀. 재처리로 같은 번호의 청크 종류가 바뀌어도 낡은 값이 남지 않게 하려는 것임. 00045가 없는 DB라서 저장이 실패하면 캡션 청크와 00045 컬럼을 빼고 다시 저장해 출처 추적은 지킴.
- **진단.** `extract.captions = {requested, captioned, failed, costUsd, featured, chunks}`
- **검사.** `npm run check:rag-caption` 46건으로 다음을 확인함.
  - 응답 정리, 청크 순서와 번호 보존, 그림 id
  - 이미지형+shadow·on 조건, 후보 이미지 한정, OCR 대기 합류
  - 크롭 OCR 콜이 바뀌지 않았는지

## 6. 한계

- **페이지 렌더 경로는 직접 재지 못함.** 측정한 크롭 70개(2장의 50개 포함)가 모두 임베드 경로에서 나옴. 골든셋 PDF가 전부 이미지 객체를 담고 있어서임. 검출 크롭(PPTX 렌더, 이미지 객체 없는 스캔)도 같은 캡션 콜을 타므로 원가는 같고, 품질은 운영 shadow 진단으로 확인함.
- **페이지 정합은 대리 지표임.** 캡션이 실제로 이미지 단위 배정에 쓸모 있는지는 Phase 1(PR G·H)과 E5에서 확인함. 계획서 R5("캡션 청크 검색 일치가 없으면 이미지형 단위를 배정하지 않음")의 근거 자료가 이 청크임.
- **그림 종류 오분류가 있음.** 혈액 도말을 'H&E 조직 사진'으로, 골수 검체 사진을 '모식도'로 적은 사례가 있음. 캡션 본문은 맞아 검색 영향은 작다고 보지만, 그림 종류만으로 거르는 용도에는 쓰지 않음.
- **비용 기록 범위.** 비교 실험 호출은 운영 `ai_cost_log`에 남기지 않음(평가 원칙, `providers.ts`와 같음). 4장의 운영 경로 확인은 하네스로 돌렸으므로 기록에 남음.

## 부록 — 후보 A 덧붙임 문구 (불채택, 운영 코드에 없음)

좌표 모드 OCR 프롬프트의 마지막 줄("그림의 선·도형·화살표는 …") 뒤에 아래를 붙였음. `CAPTION_RULES`는 `lib/rag/caption.ts`의 것과 같음.

```
- 위 JSON 에 "image" 키를 하나 더 둔다: "image":{"image_type":"<그림 종류>","caption":"<그림 설명>","findings":["<소견>"]}
- "image" 는 OCR 과 별개인 그림 설명이다. full_text·items 에는 계속 **이미지에 보이는 글자만** 넣고, 그림 설명 문장을 섞지 않는다.
<CAPTION_RULES>
```

파싱은 기존 `parseBoxedOcr`가 읽은 객체의 `image` 필드를 `parseImageCaption`으로 검사했음.
