## 0. 요약

**이번 전환은 Phase 0(공통 인덱싱) + Phase 1(후보 1 어드밴스드 RAG)까지만 진행함.** Phase 2(자가교정형)·Phase 3(그래프)은 Phase 1 종료 게이트(G1) 결과를 보고 다시 결정함.

**교수님 회신은 "나도 잘 모르는 구조이니 직접 해보며 부딪혀 보라"였음.** 그래서 v1.0 8장의 질문 Q1~Q9는 외부 답을 기다리지 않고, 우리가 실험으로 답하는 항목으로 바꿈. 각 실험의 판정 기준은 결과를 보기 전에 이 문서에 먼저 고정함(6장). 결과를 보고 기준을 바꾸면 "부딪혀 본" 게 아니라 끼워 맞춘 것이 되기 때문임.

**현행 코드를 다시 대조한 결과, v1.0이 놓친 사실이 10개 있었음(2.2).** 그중 6개(F1·F2·F3·F6·F8·F10)는 RAG를 얹기 전에 먼저 고쳐야 하는 선행 결함이라 Phase 0 범위에 넣음. 핵심은 세 가지임.

- **F1.** 텍스트 PDF·DOCX는 본문 전체가 첫 페이지 하나에 몰려 있음. 그래서 페이지 번호 기반 출처가 의미가 없음.
- **F3.** 같은 업로드를 재시도하면 청크 ID가 바뀌어 이전 문항의 출처가 끊김.
- **F6.** OCR·Vision 비용에 업로드 ID가 붙지 않아 업로드당 원가를 계산할 수 없음.

**원가 상한은 "현행 실측 문항당 원가 × 1.5"임.** 현행 실측값은 F6을 고친 뒤(Phase 0-a) 처음으로 산출할 수 있음. Phase 1은 입력 축소 효과로 오히려 원가가 내려갈 것으로 예상함.

**일정은 Phase 0 약 2주, Phase 1 약 3주로 추정함(1인 기준, v1.0 추정 유지).** 실험 예산은 Phase 0+1을 합쳐 $50 상한임.

## 3. 구현 원칙

1. **자료 기반 원칙.** 정답을 가르는 지식은 업로드 자료에서만 가져옴. 근거가 부족하면 D3대로 처리함.
2. **플래그로 전환함.** `PRIVATE_RAG_MODE=off|shadow|on`, 기본값은 `off`.
   - 파싱 방식은 기존 `PRIVATE_VERIFY_MODE`와 같은 IIFE 패턴을 따름(인식 못 하는 값은 기본값으로).
   - `off`: 현행과 동일하게 동작함. 이게 회귀 기준임.
   - `shadow`: 인덱싱·검색까지 돌려 진단에만 기록하고, 생성은 현행 경로로 함.
   - `on`: 근거 팩으로 생성함.
3. **PG 수정 범위를 명시해 둠(F9).** RAG 로직은 `lib/rag/*.ts` 잎 모듈(외부 import 없는 순수 함수 위주)에 두고 `scripts/check-rag-*.mjs`로 검사함. PG는 아래 범위만 고침.
   - Phase 0: 선행 결함 수정(0-a 계측, 0-b 추출, 0-c 청크 저장, 0-d 인덱싱 순서)
   - Phase 1: 배치 컨텍스트 선택, 생성·교정 재생성 호출 지점(근거 팩 전달), 인용 검증, 검증기 입력 교체, 근거 부족 시 예비 단위 대체와 유형 교정 재계산, 저장 필드
   - PG를 고치는 PR은 소스를 대조하는 검사 스크립트도 같은 PR에서 갱신함
4. **가용성이 검사보다 위.** 인덱싱·임베딩·검색이 실패하면 해당 업로드는 현행 full-context 경로로 폴백하고, 폴백 사유를 진단에 남김.
5. **모든 판정은 기록함.** 검색 결과·점수·인용 검증 결과·설정 스냅샷을 문항 단위로 저장해서 이후 라벨링과 Phase 2 판단의 원자료로 씀.

## 5. Phase 1 — 후보 1 어드밴스드 RAG

### 5.1 흐름

```
추출(페이지 단위) → 청킹·캡션 청크 → 임베딩 저장            [Phase 0]
→ C 출제 계획 → D 질의 생성 → E 하이브리드 검색 → F 리랭킹·압축(근거 팩)
→ G 생성(evidence_refs 필수) → H 인용 검증 → I 검증·판정기·블라인드(현행)
→ J 세트 전체 중복 검사 → K 저장(evidence·embedding·retrieval 스냅샷)
→ 유형 비율 교정·보충(현행, 근거 부족 단위는 예비 단위로 대체)
```

### 5.2 단계별 설계

**C. 출제 계획 (LLM 1콜)**
- 유형 쿼터의 권한은 계속 `type-plan.ts`가 가짐. 전역 목표, 배치별 쿼터, 보충 쿼터 모두 해당함.
- LLM 계획 콜은 출제 단위만 만듦. 출제 단위는 `{topic, objective, ask_kind 후보, needs_image, source_pages_hint}` 형식이고, `type-plan`이 준 쿼터 칸에 배정함.
- 입력: 헤딩 경로 + 페이지별 첫 2문장 + 이미지 캡션 목록, 8k 토큰 이하.
- 출력: 단위 N×1.5개. 남는 0.5N개는 D3의 예비 단위로 씀.
- 계획 콜이 실패하면 현행 `extractFocusTopics()`로 폴백함.

**D. 질의 생성**
- 단위당 질의 3개(핵심 개념 / 임상 맥락 / 감별·비교)와 HyDE 가상 발문 1개를 만듦. C단계 콜 출력에 포함되므로 추가 콜은 없음.
- HyDE 발문은 검색에만 쓰고 생성 입력에는 넣지 않음. 자료 밖 지식이 섞이는 걸 막기 위함임.
- 약어 사전은 자체 소형 사전만 씀. 시드는 두 가지임.
  - 자체 문항 `concepts`
  - `services/cpx/data/cpx/common/physical_exam_ontology.json`의 alias

**E. 하이브리드 검색** — *E3 결과 dense 단독으로 확정(sparse 불채택, [e1-e3-results.md](e1-e3-results.md)). 아래는 원래 설계임.*
- dense top-20(HNSW, 코사인)과 sparse top-20(pg_trgm, `00001`에서 이미 활성)을 RRF(k=60)로 융합함.
- 필터는 `upload_id`, 이미지 단위라면 `modality`임.
- `match_material_chunks`는 service role 전용으로 둠. RLS가 있는 테이블이라 사용자 세션에서 호출할 이유가 없음.

**F. 리랭킹·압축** — *E3 결과 리랭커 불채택, E2 결과 부모 확장 없음(1,200자 청크 6개). MMR·팩 상한은 PR H에서 적용함.*
- 리랭커는 E3 결과로 결정함. 후보는 `rerank-2.5`, `rerank-3`, 없음.
- MMR(λ=0.7)로 다양화하고, top-2는 부모(level 0) 구간으로 확장함.
- 근거 팩은 `[E1]…[E6]` 형식으로 3k 토큰 이하.
- 난이도 '상' 단위는 서로 다른 조건·지식 3개를 결합해야 하므로(`CONDITIONS_REQUIRED`) top-k를 8로 늘림.

**G. 생성**
- 툴 스키마에 `evidence_refs: [{id, quote}]`를 필수로 추가함.
  - 선택 필드로 두면 신고율이 0에 수렴함. 현행 `source_pages`를 필수로 둔 것과 같은 이유임.
- `source_pages`는 호환을 위해 남기되, 값은 `evidence_refs`에서 파생함.
- 이미지 쿼터·난이도·블라인드 교정 재생성은 전체 컨텍스트가 아니라 근거 팩만 다시 보냄(F5 해소).

**H. 인용 검증 (코드, LLM 0콜)**
- `quote`가 해당 청크 원문 안에 있는지 확인함. NFKC·공백 정규화 후 부분 일치율이 임계값 이상이어야 함. 임계값은 E4로 정하며 초기값은 0.9임.
- 불일치하면 1회 재생성하고, 다시 실패하면 폐기한 뒤 보충함.

**I. 검증·판정기·블라인드**
- 검증기의 `sourceText`를 배치 컨텍스트 앞 12,000자에서 해당 문항의 근거 팩으로 바꿈(F4 해소).
- 조건 판정기·블라인드 풀이는 현행을 유지함.

**J. 세트 전체 중복 검사**
- 문항 임베딩을 만들어 `match_private_questions`로 같은 사용자·같은 `content_sha256` 전체와 비교함. 코사인 0.92 이상이면 폐기하고 보충함.
- 이전 세션 발문 60자를 프롬프트에 넣는 현행 방식(P11)은 유지함.

**K. 저장**
- `private_questions.evidence`: `[{chunk_id, page, quote, score, rank, role}]`
- `private_questions.embedding`
- `source_refs.retrieval`: `{embed, k, fusion, reranker, topN, mmr}`
- 진단에 `configSnapshot()`

**근거 부족 처리 (D3)**
- 판정 조건: 단위의 검색 최고 점수가 τ 미만이거나, 리랭크 후 근거 팩이 비면 그 단위는 포기함. τ는 E3에서 Recall 0.9를 만족하는 점으로 정함.
- 처리 순서:
  1. 예비 단위로 대체함.
  2. 예비 단위도 소진되면 요청보다 적게 저장함.
  3. `upload-notice.ts`에 새 코드 `insufficient_evidence`를 추가해 알림을 띄움.
- 유형 비율 교정은 대체된 단위 기준으로 다시 계산함.

### 5.3 데이터 모델 스케치 (`00045`)

```sql
alter table material_chunks
  add column embedding    vector(1024),
  add column parent_id    uuid references material_chunks(id) on delete cascade,
  add column level        smallint not null default 1,      -- 0=페이지/슬라이드, 1=문단 청크
  add column modality     text not null default 'text',     -- text | ocr | image_caption | table
  add column heading_path text[],
  add column image_id     uuid;
-- kind check 확장: 'slide_text' | 'ocr' | 'image_caption'
create index idx_material_chunks_embedding on material_chunks using hnsw (embedding vector_cosine_ops);
create index idx_material_chunks_trgm      on material_chunks using gin (text gin_trgm_ops);
create function match_material_chunks(p_upload_id uuid, query_embedding vector(1024), k int, p_modality text[] default null) ...;

alter table private_questions
  add column embedding vector(1024),
  add column evidence  jsonb;
create index idx_private_questions_embedding on private_questions using hnsw (embedding vector_cosine_ops);
create function match_private_questions(p_user_id uuid, p_content_sha text, query_embedding vector(1024), threshold real, k int) ...;
```

**00045 실제 구현에서 바꾼 것(PR D):** HNSW·pg_trgm 인덱스 없음(업로드 내 정확 검색, sparse 불채택). `embedding_model`·`embedding_sha` 컬럼 추가. 저장용 RPC `rag_set_chunk_embeddings` 추가. 자세한 이유는 마이그레이션 머리말에 있음.

0-c의 결정론적 ID는 애플리케이션 쪽에서 계산하고, 마이그레이션은 기존 행을 건드리지 않음. 기존 행은 다음 재처리 때 upsert로 교체됨. 청크 ID는 내용이 바뀌면 upsert로 바뀔 수 있으므로 `parent_id` 외래키는 `ON UPDATE CASCADE`로 두거나 `(upload_id, chunk_index)`를 참조하도록 설계함.

### 5.4 원가·지연 기대 (검증 전 가설)

- 생성 입력: 배치 컨텍스트 약 6.5k → 근거 팩 3k 이하.
- 검증 입력: 12,000자 → 근거 팩.
- 교정 재생성 재전송: 전체 컨텍스트 → 근거 팩.
- 추가되는 비용: 계획 1콜(8k 이하), 임베딩(50쪽 자료 기준 $0.01 미만), 리랭크(채택 시).
- 기대: 문항당 원가는 현행과 같거나 낮고, 긴 자료일수록 유리함.
- 지연: 인덱싱과 계획 콜로 +5~10초, 배치 입력 감소로 -10~20%.
- 전부 E5에서 실측으로 확인함.

| **E1** 임베딩 | Q2 | `voyage-3`(현행 코드 기본값) / `voyage-4` / `gemini-embedding-2`, 전부 1024차원 | R1 기준 Recall@6, MRR@10 | Recall@6 최고 모델을 채택함. 1위와의 차이가 0.03 이내인 모델이 있으면 ① E3 결과와 합쳐 운영에 새로 살려야 하는 벤더 키가 적은 조합(운영 Gemini 키는 살아 있고 Voyage 키는 죽어 있음, F7) ② 단가가 낮은 쪽 순으로 고름. E1과 E3은 같은 하네스에서 함께 돌리고 함께 판정함 |
| **E2** 청킹 | Q1 | (a) level 1 1,200자 단독 (b) level 0/1 small-to-big (c) level 1 600자 + 부모 확장 | Recall@6, 근거 팩 평균 토큰 | Recall@6 최고를 채택함. 차이 0.02 이내면 토큰이 적은 쪽. 세 조건 모두 0.85 미만일 때만 level 2(문장군)를 추가 실험함 |

| **E5** A/B | Q8·Q9 | `off`(현행) vs `on`(Phase 1). 자료 10 × 10문항 × 3회 = 조건당 300문항. 요청 조건 고정(지식+임상, 난이도 중, 이미지 자료 1건은 이미지형 포함). `off` 쪽은 G0 기준선 실행을 재사용함(G0 이후 `off` 동작이 바뀌지 않았을 때만) | 7장 G1 지표 전부 | G1 기준 |

### 6.4 표본과 한계

- E5는 조건당 300문항이지만 자료 10건 안에 몰려 있어서 유효 표본은 그보다 작음. 결론은 두 가지 형태로만 보고함.
  - 전체 차이와 신뢰구간
  - 10건 중 몇 건에서 개선됐는지(자료별 일관성)
- 충실도는 LLM 판정기 값에 사람–LLM κ를 붙여 보고하고, **의학 전문가 라벨이 아님**을 명시함.
- 의미상 출처 유효성과 의학 정확성(중대·경미 오류)은 이번 범위에서 측정하지 않음. 대외 문서에서도 '측정 예정'으로만 표기함.

## 8. 원가 관리

- **기준선.** Phase 0(PR B·C) 적용 후 골든셋 10건을 `off`로 3회씩 돌린 문항당 원가의 중앙값. 헤지 패자 비용도 실제로 나가는 돈이라 포함함.
  - 문항당 원가 = 업로드 전체 AI 비용(OCR·Vision·선별 포함) ÷ 저장 문항 수
  - `docs/ops-metrics.md` 3.4의 요청 기반 산식은 QStash 경로에서 행이 생기지 않아 이번 기준선에 쓰지 않음.
  - **실측(2026-09-28, [g0-baseline.md](g0-baseline.md)).** 문항당 원가 중앙값 **$0.0241**(가중 평균 $0.0243), 업로드 처리 시간 p95 **146초**. 비용의 95.4%가 생성 호출임.
- **상한.** 기준선 × 1.5 (D2). 실측 기준으로 **문항당 $0.0362, 처리 시간 p95 219초**.
- **요금제 맥락(참고).** 내신대비 플랜은 7,900원/월, 500문항 한도임. v1.0 개산($0.10/10문항, Vision·OCR 제외, 환율 1,400원 가정)으로 계산해도 한도를 다 쓰는 학생 1인의 원가가 약 7,000원임. 현행 구조에서도 한도 소진 사용자는 요금에 근접한다는 뜻이라, 기준선 실측 뒤 요금제 원가율을 별도 안건으로 다룰 필요가 있음. 이번 범위 밖임.
  - 실측 $0.0241을 넣으면 한도 소진 학생 1인의 원가는 약 16,900원(요금의 약 2.1배)임([g0-baseline.md](g0-baseline.md) 5장).
