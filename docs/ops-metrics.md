# 운영 성능 계측 — 측정 정의와 실행 절차 (A1·A2·A4·A7)

「LectureLink 성능지표 측정 및 검증 가이드」(2026.08) **1단계 — 지금 바로 내부 측정**의
서비스 전역 구현분. 검증 분담표의 P0 항목 중 A1·A2·A4·A7을 다룬다.

CPX 축은 별도 문서(`docs/cpx-phase1-metrics.md`)에 있다. 두 축은 서비스 경계가 달라
테이블을 나누되 **산식은 같게** 맞췄다 — 같은 지표 이름이 두 대시보드에서 다른 뜻이면 안 된다.

---

## 1. 무엇이 달라졌나

이전에는 계측이 두 군데로 갈라져 있었다.

| | 있던 것 | 없던 것 |
|---|---|---|
| `ai_cost_log` | endpoint·model·비용·토큰 | `request_id`·`status`·`error_code`·소요시간 |
| 생성 진단 | 단계별 소요시간 | 조회 가능성 (업로드별 JSON 블롭) |

그래서 **성공률을 계산할 수 없었다.** AI 호출 전에 끝난 실패는 `ai_cost_log`에 행조차
남지 않아 분모가 되지 못했고, 단계별 시간은 있어도 전체 p95를 구하려면 블롭을 전부
긁어야 했다.

이제 요청 하나 = `request_metrics` 한 줄이다.

## 2. 계측이 붙는 지점

| 지점 | 무엇을 | 왜 거기인가 |
|---|---|---|
| `withErrorHandling` (`lib/utils/api.ts`) | 요청 컨텍스트 열기·닫기, 상태·오류 코드 | 62개 라우트가 전부 이걸 통과하는 단일 훅 |
| `requireSession` (`lib/auth/session.ts`) | 사용자 id | 인증은 라우트 안쪽에서 끝나 래퍼가 알 수 없다 |
| `recordAiCost` (`lib/ai/cost-cap.ts`) | 토큰·비용·모델, `ai_cost_log.request_id` | AI 호출이 반드시 지나는 지점 |
| 생성 파이프라인 (`lib/ai/private-generation.ts`) | 단계별 시간, 품질 게이트 | 이미 재던 `diag.timings`를 그대로 흘린다 |

**AsyncLocalStorage를 쓴 이유:** 계측 대상이 라우트 핸들러 안쪽 깊은 곳이다. OCR 시간은
`lib/extract` 안에서, 토큰은 `lib/ai/cost-cap` 안에서 생긴다. 이걸 전부 인자로 내려보내려면
호출 경로 전부의 시그니처를 바꿔야 한다 — 계측을 넣자고 서비스 코드를 광범위하게 고치는
것은 비용도 위험도 크다.

**계측이 서비스를 방해하지 않는다는 원칙:**
- 저장은 `after()`로 응답을 보낸 **뒤에** 돈다.
- 저장 실패는 삼키고 로그만 남긴다.
- 컨텍스트가 없으면(배치·크론·테스트) 모든 계측 호출이 조용히 no-op이다.
- `METRICS_ENABLED=false`로 끌 수 있다(끄면 1단계 실측이 사라지므로 예외 상황용).

## 3. 지표 정의 (산식과 분모)

### 3.1 성공률 / 실패율

```
성공률 = status == success 인 요청 수 / 전체 요청 수
```

| status | 조건 | 뜻 |
|---|---|---|
| `success` | 2xx·3xx | 정상 |
| `client_error` | 4xx | 사용자 입력·상태 문제 |
| `server_error` | 5xx (504 제외) | 서버·외부 API 장애 |
| `timeout` | 504 또는 timeout 계열 오류 코드 | 응답 시간 초과 |

4xx와 5xx를 나누는 이유: 하나의 '실패율'로 뭉치면 고칠 대상이 보이지 않는다.

### 3.2 지연시간

- 대시보드의 기능별 p50/p95/p99는 **성공 요청만의 분포**다.
- 백분위는 **nearest-rank** — 보간하지 않으므로 결과는 항상 실제 관측값이다.
- 표본이 적은 p95는 사실상 최댓값이다. **요청 수(n)와 함께 읽는다.**
- 기능 이름에서 uuid·숫자 세그먼트를 걷어낸다. 안 그러면 집계가 요청 수만큼 쪼개진다.
- CPX 프록시는 `cpx_proxy` 한 이름으로 접는다 — CPX 백엔드가 자기 계측을 이미 상세히 남기므로
  여기서 또 쪼개면 같은 요청이 두 대시보드에 다른 이름으로 두 번 나타난다.

### 3.3 재시도 성공률

```
회복률 = 재시도가 성공한 실패 수 / 재시도가 있었던 실패 수
이탈률 = 재시도조차 없었던 실패 수 / 전체 실패 수
```

**재시도의 정의:** 실패 뒤 **10분 안에 같은 사용자가 같은 기능을** 다시 부른 것.

요청 로그만으로 알 수 있는 것은 "다시 시도했는가"까지다. 새로고침인지 자동 재시도인지는
구분되지 않으므로 **회복률**로 읽는 것이 정확하다. 이탈률을 함께 내는 이유: 회복률만 보면
"재시도한 사람은 대체로 성공했다"는 착시가 생긴다 — 정작 중요한 건 재시도조차 안 하고
떠난 사람이다.

### 3.4 문항 1개당 원가

```
문항당 원가 = Σ(문항을 만든 요청의 비용) / Σ(그 요청들이 만든 문항 수)
```

분모가 요청이 아니라 **산출물**이다. 문항을 하나도 못 만든 요청(실패·조회)은 양쪽에서 뺀다.

### 3.5 스키마 준수율 · 중복 문항률 (A4)

```
스키마 준수율 = 위반 없는 요청 / 검사한 요청
위반율       = 위반 문항 수 / 검사한 문항 수
중복률       = 중복 의심 문항 수 / 검사한 문항 수
```

검사하지 않은 요청은 `schema_valid = null`로 남아 **분모에서 빠진다.** 검사 안 한 것과
검사해서 통과한 것을 같은 칸에 넣으면 준수율이 실제보다 좋게 나온다.

위반율·중복률의 분모는 요청이 아니라 문항이다 — 10문항 중 3개 위반과 1문항 중 3개 위반은
다른 사건이다.

**검사 항목:** 필수 필드·자료형(stem/choices/answer_index/explanation), 선지 5개,
정답 인덱스 범위, 중복 선지, 발문·해설 비어 있지 않음, 그리고 기존 `lintKmleQuestion`의
형식 규격(F01~) 위반.

**중복 판정 두 모드:**
- `embedding` — 벡터가 있는 경로(공용 문제은행)는 코사인 유사도.
- `lexical` — 벡터가 없는 경로는 문자 트라이그램 Jaccard. `private_questions`에는 embedding
  컬럼이 없고, 임베딩을 새로 뽑으면 문항마다 API 비용이 붙는다. 재생성 중복은 표현까지 거의
  같게 나오는 편이라 어휘 유사도로 잡힌다. **다만 근사다** — 뜻만 같고 표현이 다른 중복은
  놓친다. 이 한계는 수치를 보고할 때 함께 밝힌다.

임계는 `DUPLICATE_SIMILARITY_THRESHOLD`(0.92). 임계를 바꾸면 중복률의 의미가 바뀌므로
계측 레코드에 임계값을 함께 남긴다.

**막지 않고 표시한다.** 저장을 거절하면 이미 생성 비용을 치른 문항이 사라지고 사용자는
"10문항 요청했는데 7개만 나왔다"를 본다. 무엇을 버릴지는 코드가 아니라 사람의 판단이다.

## 4. 데이터셋 분리와 버전 고정 (A7)

### 4.1 프롬프트 버전

`lib/ai/versions.ts`의 `PROMPT_VERSIONS`가 기능별 프롬프트 세대를 센다. 계측 레코드의
`version` 컬럼이 이 값을 받는다.

**프롬프트를 고치면 버전을 올린다.** 올리지 않으면 서로 다른 두 설정의 수치가 한 축으로
뭉쳐, 그 이후의 모든 비교가 조용히 틀린다. 올리는 기준은 *판정이나 산출물의 성격이 바뀌는*
정도의 변경 — 오타 수정은 올리지 않는다(버전이 의미 없이 늘면 비교축이 부서진다).

`configSnapshot()`이 재현 조건(프롬프트 세대·임베딩 모델·중복 임계·모델 id)을 한 객체로
내놓고, 대시보드 하단에 그대로 표시된다. 보고서에 이 스냅샷을 함께 싣는다.

### 4.2 데이터셋 레지스트리

`datasets/manifest.json`이 개발셋·검증셋·최종 테스트셋을 등록한다.
`npm run check:datasets`가 CI에서 검사하는 것:

1. 잠긴(`locked`) 테스트셋의 내용이 **바뀌지 않았는지** (sha256 고정)
2. 같은 경로가 두 갈래에 등록되지 않았는지 (누수)
3. 잠긴 항목에 해시가 있는지

**왜 잠그나:** 테스트셋을 조금씩 고치면 점수가 오른다. 고의가 아니어도 그렇다 — 애매한
항목을 지우고 잘 도는 항목을 남기는 방향으로 손이 간다. 해시를 박아 두면 그 변경이 CI에서
눈에 띄고, 정당한 변경이면 새 id로 등록하게 된다.

봉인: `npm run check:datasets -- --lock <id>`

**코드가 강제할 수 없는 것:** "결과를 보고 프롬프트를 고쳤는가". 이건 사람의 규율이다.
가이드 §10.2가 금지하는 행위이고, 문서로만 남긴다.

## 5. 실행 절차

### 5.1 배포

```
METRICS_ENABLED=true          # 기본값
```

마이그레이션 `00042_request_metrics.sql`을 적용한다. `request_metrics` 테이블,
`ai_cost_log.request_id` 컬럼, `purge_request_metrics()` 함수가 만들어진다.

보존 기간은 90일이며 관리자 대시보드가 열릴 때 정리된다. 요청 경로에 붙이지 않은 이유는
계측 정리가 서비스보다 비싸지면 안 되기 때문이다. **90일보다 긴 기간을 보고에 쓰려면
정리 전에 요약을 따로 내보내 둔다.**

### 5.2 대시보드

관리자 계정으로 **`/admin/metrics`** (1일 / 7일 / 30일). CPX 축은 `/admin/cpx-metrics`.

표본이 상한(20,000건)에서 잘리면 화면에 밝힌다 — 조용히 자르면 "이 기간 성공률"이 사실은
최근 일부의 성공률이 된다.

### 5.3 자동 회귀 테스트

`.github/workflows/metrics-ci.yml`이 관련 변경마다 실행한다.

```bash
npm run check:metrics    # 산식 51개 검사 (백분위·분모·재시도·기능 이름·품질 게이트)
npm run check:datasets   # 데이터 누수 방지
```

## 6. 발표에 쓸 때의 주의

1. **표본 수를 함께 낸다.** n이 두 자리인 p95는 성능 주장으로 쓰지 않는다.
2. **기간과 버전을 밝힌다.** `configSnapshot()`을 그대로 붙인다.
3. **실패 사례도 낸다.** 오류 코드 분포와 이탈률을 함께 보인다.
4. **중복률은 근사임을 밝힌다.** 내신대비 경로는 어휘 유사도 기반이라 의미상 중복을 놓친다.
5. **1단계 수치는 운영 지표까지다.** 문항의 의학적 타당성·근거 충실도는 2단계이며 전문가
   없이 낼 수 없다. 이 대시보드에 "정확도"라 부를 수치는 없다.

## 7. 아직 안 된 것

- **실측값 0.** 마이그레이션 적용 후 실제 트래픽이 돌아야 채워진다.
- **A3 문항 생성 반복 안정성 하네스** — 고정 입력셋 20–30건 선정이 선행.
- **A5 OCR 골든셋 100–150장 전사** — 측정기·층화 목표·검사기·작업 안내는 준비됐다
  (`datasets/ocr-goldenset/README.md`). 남은 것은 전사뿐이고, 실제 강의자료가 있어야 한다.
  진척은 `npm run check:ocr-goldenset` 으로 보고, 다 모으면 `--complete` 로 완성 판정한 뒤
  `--lock ocr-goldenset-v1` 로 봉인한다.
- **A8·A9 출처 추적·검색 계층** — 2단계 전체의 선행 조건. 이것 없이는 근거 충실도·
  Recall@K를 잴 대상 자체가 없다.
