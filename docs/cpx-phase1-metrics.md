# CPX 1단계 성능지표 실측 — 측정 정의와 실행 절차

「LectureLink 성능지표 측정 및 검증 가이드」(2026.08) **1단계 — 지금 바로 내부 측정**의
CPX 서비스 구현분이다. 가이드가 1단계 결과물로 요구한 두 가지, **운영 대시보드**와
**자동 회귀 테스트**를 함께 만든다.

> 가이드 §10.3: 대외 발표에는 표본 수, 라벨링 기준, 신뢰구간을 함께 제시한다.
> 이 문서는 각 수치가 **무엇을 세고 무엇을 빼는지**를 고정한다. 산식이 코드와 문서에서
> 갈라지면 발표 수치를 방어할 수 없다.

---

## 1. 무엇을 재고 무엇을 못 재는가

| 가이드 1단계 항목 | CPX에서의 구현 | 상태 |
|---|---|---|
| 생성 성공률·실패율 | 모든 `/api/*` 요청 1건 = `request_metrics` 1행 | 구현 |
| p50 / p95 / p99 지연시간 | `request_metrics.total_ms` + 단계별 `stages` | 구현 |
| 오류 코드별 빈도 | `request_metrics.error_code` | 구현 |
| 문항·세션당 비용 | `usage_events` 토큰 실측 × 단가표(`usage.py`) | 기존 + 집계 추가 |
| 스키마 준수율 | 채점 결과 JSON 계약 검사 → `schema_valid` | 구현 |
| 반복 생성 안정성 | 고정 전사 N회 재채점 (`repeatability.py`) | 구현 |
| CPX 세션 완주율 | `sessions.end_reason` + 이탈 판정 | 구현 |
| CPX 턴 응답시간 | 클라이언트 실측 → `turn_metrics` | 구현 |
| 자료 처리 성공률 | **해당 없음** — CPX는 사용자 자료를 처리하지 않는다 (내신대비 축) |
| 중복 문항률 | **해당 없음** — CPX는 문항을 생성하지 않는다 |

측정할 수 없는 것을 분명히 해 둔다.

- **AI 환자 응답의 반복 안정성은 잴 수 없다.** 대화는 학생 질문에 따라 매번 달라 같은
  입력을 만들 수 없다. 반복 안정성 측정 대상은 **채점**이다 — 고정된 전사에서 항상 같은
  판정이 나오는지. (AI 환자의 일관성은 2단계 '정보 슬롯 F1'이 담당한다.)
- **서버는 턴 지연을 관측하지 못한다.** Live 오디오는 브라우저와 Gemini 사이에서 직접
  오간다. 턴 응답시간은 전부 클라이언트 측정치이고, 서버는 범위만 강제한다.
- **완주율은 Fly SQLite 기준이다.** Supabase 미러의 스윕 정산과 숫자가 다를 수 있다.

## 2. 지표 정의 (산식과 분모)

### 2.1 요청 성공률 / 실패율

```
성공률 = status == success 인 요청 수 / 전체 요청 수
```

`status` 분류:

| 값 | 조건 | 뜻 |
|---|---|---|
| `success` | 2xx·3xx | 정상 |
| `client_error` | 4xx | 사용자 입력·상태 문제 (없는 케이스, 진행 중 세션 채점) |
| `server_error` | 5xx (504 제외) | 서버·외부 API 장애 |
| `timeout` | 504 또는 `evaluate_timeout` | 응답 시간 초과 |

4xx와 5xx를 나누는 이유: 둘을 하나의 '실패율'로 뭉치면 고쳐야 할 대상이 보이지 않는다.
404가 늘어난 것과 502가 늘어난 것은 전혀 다른 사건이다.

### 2.2 지연시간

- 대시보드의 기능별 p50/p95/p99는 **성공 요청만의 분포**다. 실패는 즉시 끊기거나(4xx)
  타임아웃 상한에 붙어(504) 분포를 양쪽으로 왜곡한다.
- 백분위는 **nearest-rank**다. 보간하지 않으므로 결과는 항상 실제 관측값이다.
- 표본 5개에서 뽑은 p95는 사실상 최댓값이다. **요청 수(n)와 함께 읽는다.**
- 단계별(`stages`) 기록: 채점은 `load` → `llm_extract` → `scoring` → `persist`,
  캐시 재조회는 `cache_hit`, 토큰 발급은 `token_create`.

### 2.3 세션 완주율

```
완주율 = (completed + time_limit) / (전체 - start_failed - superseded - active)
```

| 종료 사유 | 뜻 | 완주 | 분모 |
|---|---|---|---|
| `completed` | 학생이 [진료 종료]를 누름 | ✅ | 포함 |
| `time_limit` | 제한시간 소진 자동 종료 | ✅ | 포함 |
| `aborted` | 중도 이탈 (클라이언트가 명시) | ❌ | 포함 |
| `abandoned` | `/end` 없이 제한시간+15분 초과 (집계 시 판정) | ❌ | 포함 |
| `start_failed` | 연결·마이크 실패로 시작 직후 반납 | ❌ | **제외** |
| `superseded` | 새 연습을 위해 이전 세션 정리 | ❌ | **제외** |
| `active` | 아직 진행 중 | — | **제외** |
| `unknown` | 사유 없이 종료 (이 기능 이전 세션) | ❌ | 포함 |

**제한시간 종료를 완주로 세는 이유:** 실제 CPX 시험에서 12분 종료는 정상적인 마무리다.
중단이 아니다.

**시작 실패를 분모에서 빼는 이유:** 진료를 해 볼 기회조차 없던 세션을 '미완주'로 세면
완주율이 연결 장애율과 뒤섞여 무엇을 고쳐야 하는지 가리킨다. 대신 `startFailureRate`로
따로 보고한다.

**`abandoned` 판정:** 이탈은 정책상 '자동 일시정지'라 클라이언트가 `/end`를 부르지 않는다
(CPX 시간 차감 정책 7장). 그래서 집계 시점에 시간으로 판정한다 —
`지금 - 시작시각 > 제한시간 + 15분`이면 이탈.

**표본이 없으면 `null`이다.** 0%가 아니다. 진행 중인 세션만 있는데 완주율 0%로 보고하면
거짓말이 된다.

### 2.4 턴 응답시간

클라이언트(`components/cpx/live.js`)가 턴마다 세 값을 잰다.

| 값 | 정의 |
|---|---|
| `firstResponseMs` | 발화 종료 → 첫 응답 신호(전사 또는 오디오) |
| `firstAudioMs` | 발화 종료 → 첫 오디오 바이트 (학생이 "환자가 말을 시작했다"고 느끼는 시점) |
| `turnCompleteMs` | 발화 종료 → `turnComplete` |

**'발화 종료'의 정의:** Gemini Live는 서버 VAD로 턴을 끊고 발화 종료를 따로 통지하지
않는다. 그래서 **응답이 시작되기 직전 마지막으로 도착한 입력 전사의 시각**을 발화 종료로
삼는다. 텍스트 문진은 전송 시각이 곧 발화 종료다(`inputMode: text`).

측정에서 빠지는 턴:

- **연결이 끊긴 채 미완인 턴** — 재연결 후 `turnComplete`가 오면 '몇 분짜리 응답'으로
  기록돼 p95가 통째로 망가진다. `disconnect()`에서 버린다.
- **빈 `turnComplete`** — 이전 턴 interrupt의 잔향이라 응답이 없다.
- 끼어들기로 잘린 턴은 **남기되** `interrupted`로 표시해 집계에서 구분한다.

시계는 `performance.now()`다. `Date.now()`는 시스템 시각 보정에 따라 뒤로 갈 수 있어
음수 지연이 나온다. 서버도 음수와 10분 초과 값을 422로 거절한다.

네트워크 상태(`effectiveType`)별로도 쪼개 본다 — 가이드 §2.1이 요구하는 세부 결과다.

### 2.5 세션당 원가

```
세션당 평균 원가 = Σ(턴이 1개 이상인 세션의 원가) / 그 세션 수
```

턴이 없던 세션(연결 실패)은 분모에서 뺀다. 0원 세션이 섞이면 "한 세션에 얼마 드는가"의
답이 실제보다 싸게 나온다. Live 대화분과 채점 호출분을 나눠 보고한다.

### 2.6 스키마 준수율

```
준수율 = 계약을 지킨 채점 결과 수 / 스키마 검사 대상 응답 수
```

채점 결과 JSON은 결과 화면과 Supabase 미러가 함께 쓰는 계약이다. 검사 항목:
필수 필드 8개(`totalScore`, `sections`, `feedback`, `judgments`, `caseId`, `itemTexts`,
`timeAnalysis`, `clinicalReasoning`) 존재와 자료형, `totalScore` 0–100 범위,
`sections` 비어 있지 않음, 각 섹션의 `id`/`name`/`score`/`weightPercent` 존재와 자료형.

**위반해도 응답은 막지 않는다.** 여기서 502를 내면 이미 돈과 시간을 쓴 채점이 통째로
버려지고 학생은 결과를 못 본다. 계측에 남기고 서버 로그에 위반 항목을 띄운다.

### 2.7 반복 생성 안정성

고정 전사(`fixtures/repeatability_transcript.json`)로 채점을 N회(가이드 기준 최소 10회)
반복해 변동을 잰다.

| 지표 | 정의 | 자체 기준 |
|---|---|---|
| 스키마 준수율 | 계약을 지킨 실행 비율 | 1.00 |
| 항목 판정 일치도 | 항목별 최빈 판정 비율의 평균 | ≥ 0.95 |
| 총점 표준편차 | 100점 만점 기준 모표준편차 | ≤ 2.0 |
| 근거 인용 일치도 | 항목별 '근거 있음/없음'의 최빈 비율 평균 | 참고 |
| 위반 판정 동일 비율 | 위반 집합이 최빈값과 같은 실행 비율 | 참고 |
| 실행시간 | p50 / p95 | 참고 |

기준 미달은 실패가 아니라 **보고 대상**이다. 1단계 목표는 "얼마나 흔들리는지 안다"이고,
미달이면 원인(모델, 프롬프트, thinking budget)을 함께 적는다.

## 3. 실행 절차

### 3.1 배포 (계측 켜기)

CPX FastAPI 환경변수:

```
CPX_FEATURE_VERSION=cpx-v1       # 배포마다 올린다 (커밋 해시 가능) — 버전 간 회귀 비교축
CPX_METRICS_ENABLED=true         # 기본값. 끄면 1단계 실측이 통째로 사라진다
CPX_METRICS_RETENTION_DAYS=90    # 이보다 오래된 계측 행은 1시간에 한 번 정리된다
```

테이블(`request_metrics`, `turn_metrics`)과 `sessions.end_reason` 컬럼은 프로세스 시작 시
자동 생성·마이그레이션된다. 별도 SQL 적용은 없다.

보존 기간을 두는 이유: 계측은 요청마다 한 줄씩 쌓인다. 하트비트와 3초 flush 까지 세면
12분 세션 하나가 수백 행이고, 단일 컨테이너 SQLite 볼륨에서 이걸 영원히 두면 디스크가 찬다.
정리는 요청 처리 뒤에 붙어 돌지만 1시간에 한 번으로 제한된다 — 계측이 서비스보다 비싸지면
안 된다. **90일보다 긴 기간을 발표에 쓰려면 정리 전에 요약을 따로 내보내 둔다.**

### 3.2 대시보드

LectureLink 관리자 계정으로 **`/admin/cpx-metrics`** (기간: 1일 / 7일 / 30일).

권한은 이중 잠금이다. ① CPX 백엔드는 프록시 공유 비밀이 없는 요청을 받지 않는다.
② 그 위에 `x-cpx-admin: 1` 헤더를 요구하고, 이 헤더는 `requireAdmin()`을 통과한
Next.js 서버 컴포넌트만 붙인다. 헤더가 없으면 403 — 열린 쪽으로 실패하지 않는다.

### 3.3 반복 안정성 측정 (모델 호출 필요)

```bash
cd services/cpx/server
GEMINI_API_KEY=... venv/bin/python repeatability.py --runs 10 \
  --out ../../../outputs/cpx-repeatability.json
```

모델이나 프롬프트를 바꾼 뒤에는 **같은 고정 입력으로** 다시 돌려 비교한다.

### 3.4 자동 회귀 테스트

`.github/workflows/cpx-ci.yml`의 `patient-engine` 잡이 CPX 관련 변경마다 실행한다.

```bash
venv/bin/python test_metrics.py             # 계측 13그룹
venv/bin/python repeatability.py --selftest # 변동 산식 (API 키 불필요)
```

## 4. 발표에 쓸 때의 주의

가이드 §10.3과 §12.3을 그대로 적용한다.

1. **표본 수를 함께 낸다.** p95는 요청 수와 함께 읽는다. n이 두 자리면 p95를 성능
   주장으로 쓰지 않는다.
2. **기간과 버전을 밝힌다.** `CPX_FEATURE_VERSION`과 창(1/7/30일), 모델명을 함께 적는다.
3. **실패 사례도 낸다.** 오류 코드 분포와 완주하지 못한 세션의 사유 분포를 함께 보인다.
4. **완주율의 분모를 밝힌다.** 시작 실패·재시작·진행 중 세션을 뺀 값이다.
5. **1단계 수치는 운영 지표까지다.** 채점 정확도·환자 일관성·교육 효과는 2·3단계이며,
   전문가·실사용자 없이 낼 수 없다. 1단계 대시보드에 "정확도"라고 부를 수치는 없다.
